# Upgrade Guide: Kontent.Ai.Delivery 19 → 20

This guide covers upgrading from `Kontent.Ai.Delivery` **19.x** to **20.0**, and the `Kontent.Ai.Delivery.Caching`
and `Kontent.Ai.Delivery.SourceGeneration` packages that ship with it.

Coming from 18.x? Follow [18 → 19](18-to-19.md) first; it is the large one. Guides cover one major each and
are read in sequence.

The major exists because the packages move to .NET 10. The registration surface was rewritten in the same
release, while the line was still in release candidates, and the paging contract changed so that a failed
page cannot be mistaken for the end of a walk. Everything else you wrote against 19 - queries, filters,
models, rich text, response handling - is untouched. For most applications the compile-time work is under
an hour: one registration block, one caching call per client, and a rebuild.

Two changes compile unchanged and behave differently at runtime. Read [§2](#2-a-failed-page-throws) and
[§3](#3-transport-failures-are-results-cancellation-throws) even if the compiler is quiet.

## At a glance

| Change | Effort |
|---|---|
| `net8.0` → `net10.0` | Move your project to .NET 10 first; see [§1](#1-target-net-10) |
| `EnumerateAsync()` throws on a failed page instead of stopping | Add a `catch`, or use `ExecuteAsync`; see [§2](#2-a-failed-page-throws) |
| `QueryEnumerationExtensions` / `EnumerateItemsWithStatusAsync` removed | `EnumerateAsync().AsPages()` in a `try`/`catch`; see [§2](#2-a-failed-page-throws) |
| Transport failures are results; only cancellation throws | Read `IsSuccess` where you caught `HttpRequestException`; see [§3](#3-transport-failures-are-results-cancellation-throws) |
| `AddDeliveryClient` takes a builder | `AddDeliveryClient(o => …)` becomes `AddDeliveryClient(delivery => delivery.Options.Configure(o => …))`; see [§4](#4-registration-is-one-builder) for every form |
| `DeliveryClientBuilder` → `DeliveryClient.Create` | Same builder as the DI path, over a private container; see [§4.2](#42-the-standalone-client) |
| `IDeliveryOptionsBuilder` / `DeliveryOptionsBuilder` removed | Set properties; `UsePreviewApi` / `UseProductionApi` / `UseCustomEndpoint` are extension methods on `DeliveryOptions`; see [§4.3](#43-the-options-builder) |
| Caching attaches to the builder | `AddDeliveryMemoryCache(...)` becomes `delivery.UseMemoryCache(...)`; see [§5](#5-caching-attaches-to-the-builder) |
| Custom `IDeliveryCacheManager`: `null` from the factory means "gone", a throw means "unreachable" | Review your manager if you keep stale copies; see [§5.3](#53-custom-cache-managers) |
| `IDisposable` off `IDeliveryClient` | Keep the standalone client as `var`; see [§6](#6-disposal-moved-to-the-concrete-client) |
| `DeliveryClientFactory`, `IItemTypingStrategy`, `RefitSettingsProvider` internal; `IContentDeserializer` removed | See [§7](#7-removed-from-the-public-api) |
| `configureRefit` parameter removed | Delete the argument |
| Redis keys change shape | Nothing to do; old entries expire unread; see [§5.4](#54-distributed-cache-keys) |

## 1. Target .NET 10

There is no multi-targeting. A project on .NET 8 cannot install 20.0 at all - restore fails with
`NU1202: Package Kontent.Ai.Delivery is not compatible with net8.0`.

```xml
<TargetFramework>net10.0</TargetFramework>
```

`Kontent.Ai.Delivery.SourceGeneration` stays `netstandard2.0`, as Roslyn components must, and loads in every
SDK from .NET 8.0.2xx onward.

The dependency floors move with the framework: `Microsoft.Extensions.*` to 10.0, `Refit` to 15.2, `AngleSharp`
to 1.7, `ZiggyCreatures.FusionCache` to 2.6. An application that pins an older Refit alongside the package
must move too.

## 2. A failed page throws

**This compiles unchanged and behaves differently.** In 19, `EnumerateAsync()` on the feed and used-in queries
ended its loop when a page request failed and yielded nothing to say so: an export or a search-index build
could persist a partial result and never know. In 20 it throws `DeliveryRequestException`, carrying the
status code, the API's `IError`, the request ID and the request URL.

```csharp
// 19 - a failed page ended the loop quietly
await foreach (var article in client.GetItemsFeed<Article>().EnumerateAsync())
{
    Index(article);
}

// 20 - a failed page throws; catch it where a failure belongs in your log
try
{
    await foreach (var article in client.GetItemsFeed<Article>().EnumerateAsync())
    {
        Index(article);
    }
}
catch (DeliveryRequestException ex)
{
    logger.LogError(ex, "Feed walk failed with {StatusCode}", ex.StatusCode);
}
```

Where a failure should be a value rather than an exception, use the single-request `ExecuteAsync()`, which
still reports it as `IsSuccess = false`.

`EnumerateAsync()` now returns `DeliveryEnumeration<T>` rather than `IAsyncEnumerable<T>`. It *is* an
`IAsyncEnumerable<T>`, so `await foreach` over items needs only a recompile. It also offers
`AsPages(continuationToken)`, a page view that exposes the continuation token, so a walk can be checkpointed
and resumed - which no route could do in 19.

`QueryEnumerationExtensions` and its four `EnumerateItemsWithStatusAsync` overloads are removed. They existed
only because the walk could not report failure. The replacement is `AsPages()`, and it is not a rename: the
element type changes from `IDeliveryResult<…>` to `DeliveryPage<T>`, and the `if (!page.IsSuccess)` branch
becomes a `catch`.

```csharp
// 19
await foreach (var page in query.EnumerateItemsWithStatusAsync())
{
    if (!page.IsSuccess) { Handle(page.Error); break; }
    Process(page.Value.Items);
}

// 20
try
{
    await foreach (var page in query.EnumerateAsync().AsPages())
    {
        Process(page.Items);
    }
}
catch (DeliveryRequestException ex) { Handle(ex); }
```

The `PaginationStoppedEarly` warning (event ID `1051`) is retired with it. Anything alerting on that event
should move to the exception, or to `QueryFailed`, which a failed page still emits.

## 3. Transport failures are results; cancellation throws

**This compiles unchanged and behaves differently.** In 19 a DNS failure, a refused connection or a
resilience-pipeline rejection threw out of the query. In 20 they arrive as an unsuccessful result carrying
the exception, the way every other failure in this SDK is reported: `IsSuccess` is `false`, `StatusCode` is
`0` (no response was received), `Error.Message` carries the exception's own message and `Error.Exception`
the exception.

```csharp
// 19
try
{
    var result = await client.GetItem<Article>("on_roasts").ExecuteAsync();
}
catch (HttpRequestException ex) { … }   // never fires in 20

// 20
var result = await client.GetItem<Article>("on_roasts").ExecuteAsync();
if (!result.IsSuccess)
{
    // result.StatusCode == 0 for a transport failure; result.Error.Exception carries it
}
```

Cancellation is the one exception. When your token fires, `OperationCanceledException` is thrown, so
`Task.IsCanceled`, `Task.WhenAll` and cancellation handlers behave as they do everywhere in .NET. An expired
`HttpClient.Timeout` is *not* cancellation: the request was sent, so it is a failed result like any other
transport failure.

## 4. Registration is one builder

19 had twelve `AddDeliveryClient` overloads - one per way of supplying options, doubled for named clients,
with the HTTP and resilience hooks as trailing parameters - plus `DeliveryClientBuilder` and
`IDeliveryOptionsBuilder` for the container-free case. 20 has three `AddDeliveryClient` overloads and one
`DeliveryClient.Create`, all taking the same `IDeliveryClientBuilder`. What used to be a parameter is a
member on it:

- `Options` - the client's `OptionsBuilder<DeliveryOptions>`: `Configure`, `Configure<TDependency>`, `Bind`,
  `BindConfiguration`, `Validate`.
- `HttpClient` - the `IHttpClientBuilder` the transport is built on; every `Microsoft.Extensions.Http`
  extension applies. Handlers you add run after the SDK's own and re-run on every retry.
- `ConfigureResilience(...)` - replaces the default pipeline.
- `Services` and `Name` - for anything attached to this client by hand: a custom `ITypeProvider`, a logger
  factory, a cache.

### 4.1 Every registration form

| 19 | 20 |
|---|---|
| `AddDeliveryClient(o => …)` | `AddDeliveryClient(delivery => delivery.Options.Configure(o => …))` |
| `AddDeliveryClient((sp, o) => …)` | `delivery.Options.Configure<TDependency>((o, dep) => …)` |
| `AddDeliveryClient(b => b.WithEnvironmentId(id).UsePreviewApi(k).Build())` | `delivery.Options.Configure(o => { o.EnvironmentId = id; o.UsePreviewApi(k); })` |
| `AddDeliveryClient(configuration)`, `(configuration, "Section")` | `delivery.Options.BindConfiguration("DeliveryOptions")` in a host; otherwise `delivery.Options.Bind(configuration.GetSection(…))` |
| `AddDeliveryClient(section)` | `delivery.Options.Bind(section)` |
| `AddDeliveryClient(options)` | unchanged; an optional builder callback runs after the instance is copied |
| `AddDeliveryClient("name", …)` | `AddDeliveryClient("name", delivery => …)` |
| `AddDeliveryClient("name", options)` | `AddDeliveryClient("name", delivery => delivery.Options.Configure(options.CopyTo))` |
| `configureHttpClient: b => …` | `delivery.HttpClient.…` |
| `configureResilience: p => …` | `delivery.ConfigureResilience(p => …)` |
| `configureRefit: …` | removed; everything it reached was load-bearing rather than configurable |

`Options.Configure(...)` returns the `OptionsBuilder`, not the client builder, so several steps go in a
statement lambda:

```csharp
services.AddDeliveryClient("preview", delivery =>
{
    delivery.Options.BindConfiguration("Delivery:Preview");
    delivery.ConfigureResilience(pipeline => pipeline.AddRetry(new HttpRetryStrategyOptions { MaxRetryAttempts = 5 }));
    delivery.HttpClient.AddHttpMessageHandler<AuditingHandler>();
});
```

Binding from configuration keeps its change token, so a reloaded API key takes effect without rebuilding the
client, as before. The default client's options also resolve as the unnamed `IOptions<DeliveryOptions>` and
follow the same reloads.

One sample that used to appear in this SDK's docs is worth removing from yours:
`delivery.HttpClient.ConfigureHttpClient(c => c.Timeout = …)` runs after the SDK's own configuration and
silently caps the whole retry sequence. `DeliveryOptions.Timeout` is the whole-call ceiling and always wins.

### 4.2 The standalone client

`DeliveryClientBuilder` is gone. `DeliveryClient.Create` takes the same builder and runs it over a private
container the client owns, so every DI-side feature is available without a container of your own.

```csharp
// 19
await using var client = DeliveryClientBuilder
    .WithOptions(b => b.WithEnvironmentId("…").UseProductionApi().Build())
    .WithTypeProvider(new GeneratedTypeProvider())
    .WithLoggerFactory(loggerFactory)
    .WithMemoryCache(TimeSpan.FromHours(1))
    .ConfigureServices(s => s.AddSingleton<IMyDependency, MyImpl>())
    .Build();

// 20
await using var client = DeliveryClient.Create(delivery =>
{
    delivery.Options.Configure(o => { o.EnvironmentId = "…"; o.UseProductionApi(); });
    delivery.Services.AddSingleton<ITypeProvider>(new GeneratedTypeProvider());
    delivery.Services.AddSingleton(loggerFactory);
    delivery.UseMemoryCache(cache => cache.DefaultExpiration = TimeSpan.FromHours(1));
    delivery.Services.AddSingleton<IMyDependency, MyImpl>();
});

// or from a pre-built options instance
await using var client = DeliveryClient.Create(new DeliveryOptions { EnvironmentId = "…" }.UseProductionApi());
```

| `DeliveryClientBuilder` member | 20 |
|---|---|
| `WithOptions(Func<IDeliveryOptionsBuilder, DeliveryOptions>)` | `delivery.Options.Configure(...)`, or `Create(options)` |
| `WithTypeProvider(ITypeProvider)` | `delivery.Services.AddSingleton<ITypeProvider>(provider)` |
| `WithLoggerFactory(ILoggerFactory)` | `delivery.Services.AddSingleton(factory)`, or `delivery.Services.AddLogging(...)` |
| `WithMemoryCache(...)` / `WithHybridCache(distributedCache, ...)` | `delivery.UseMemoryCache(...)` / `delivery.UseHybridCache(...)`; see [§5](#5-caching-attaches-to-the-builder) |
| `ConfigureServices(Action<IServiceCollection>)` | `delivery.Services` |
| `Build()` | the `Create` call returns the client |

`Create` throws `OptionsValidationException` on invalid options, as `Build()` did. The returned
`DeliveryClient` is disposable; the interface is not ([§6](#6-disposal-moved-to-the-concrete-client)).

### 4.3 The options builder

`IDeliveryOptionsBuilder` and `DeliveryOptionsBuilder` are gone. Members that set one property are that
property; the ones that set two survive as extension methods on `DeliveryOptions`.

| `IDeliveryOptionsBuilder` member | 20 |
|---|---|
| `WithEnvironmentId(string \| Guid)` | `EnvironmentId = "…"` |
| `WithTimeout(TimeSpan)` | `Timeout = …` |
| `DisableRetryPolicy()` | `EnableResilience = false` |
| `WithCustomAssetDomain(string \| Uri)` | `CustomAssetDomain = "…"` |
| `WithDefaultRenditionPreset(string)` | `DefaultRenditionPreset = "…"` |
| `UsePreviewApi(key)` | `UsePreviewApi(key)` - extension method, same name |
| `UseProductionApi()`, `UseProductionApi(secureAccessKey)` | same names, extension methods |
| `WithCustomEndpoint(string \| Uri)` | `UseCustomEndpoint(...)` |
| `Build()` | nothing; the options object is the result |

```csharp
// 19
var options = DeliveryOptionsBuilder.CreateInstance()
    .WithEnvironmentId("…")
    .UseProductionApi(secureKey)
    .WithTimeout(TimeSpan.FromMinutes(5))
    .Build();

// 20
var options = new DeliveryOptions { EnvironmentId = "…", Timeout = TimeSpan.FromMinutes(5) }
    .UseProductionApi(secureKey);
```

## 5. Caching attaches to the builder

The twelve `AddDeliveryMemoryCache` / `AddDeliveryHybridCache` / `AddDeliveryCacheManager` overloads on
`IServiceCollection` and the six `WithMemoryCache` / `WithHybridCache` methods on the standalone builder become
five methods on `IDeliveryClientBuilder`. A cache is configured where its client is registered, in both hosting
modes.

| 19 | 20 |
|---|---|
| `services.AddDeliveryMemoryCache(defaultExpiration: …)` | `delivery.UseMemoryCache(cache => cache.DefaultExpiration = …)` |
| `services.AddDeliveryMemoryCache("name", …)` | `delivery.UseMemoryCache(...)` inside that client's callback |
| `services.AddDeliveryMemoryCache((sp, o) => …)` | `delivery.UseMemoryCache((sp, cache) => …)` |
| `services.AddDeliveryHybridCache(...)` | `delivery.UseHybridCache(...)`; the `IDistributedCache` is read from `Services` |
| `services.AddDeliveryCacheManager(sp => …)` | `delivery.UseCacheManager(sp => …)` |
| `.WithHybridCache(distributedCache, …)` on the standalone builder | register the cache on `delivery.Services`, then `delivery.UseHybridCache(...)` |
| `keyPrefix:` / `defaultExpiration:` parameters | `DeliveryCacheOptions.KeyPrefix` / `.DefaultExpiration` in the configure delegate |

```csharp
// 19
services.AddDeliveryClient("preview", o => { o.EnvironmentId = "…"; o.UsePreviewApi = true; o.PreviewApiKey = "…"; });
services.AddDeliveryMemoryCache("preview", defaultExpiration: TimeSpan.FromMinutes(30));

// 20
services.AddDeliveryClient("preview", delivery =>
{
    delivery.Options.Configure(o => { o.EnvironmentId = "…"; o.UsePreviewApi("…"); });
    delivery.UseMemoryCache(cache => cache.DefaultExpiration = TimeSpan.FromMinutes(30));
});
```

One split the old registrations allowed is gone: a library registering the client and the application adding
a cache to it in a separate step. Whoever registers the client owns its cache.

### 5.1 Reaching the cache manager

A named client's manager is keyed by its name, as before. Two routes are new. The default client's manager
resolves unkeyed - in 19 its key was an internal constant - and a standalone client exposes its own:

```csharp
var cacheManager = serviceProvider.GetRequiredService<IDeliveryCacheManager>();                  // default client
var cacheManager = serviceProvider.GetRequiredKeyedService<IDeliveryCacheManager>("production"); // named client
var cacheManager = standaloneClient.CacheManager;                                                  // DeliveryClient.Create
```

### 5.2 Dependency keys

`DeliveryCacheDependencies` composes the keys the SDK tags with, so a webhook handler no longer writes
`"item_" + codename` by hand, and `InvalidateAsync` matches keys case-insensitively:

```csharp
// 19
await cacheManager.InvalidateAsync([$"item_{codename}", DeliveryCacheDependencies.ItemsListScope]);

// 20
await cacheManager.InvalidateAsync([DeliveryCacheDependencies.ForItem(codename), DeliveryCacheDependencies.ItemsListScope]);
```

The 19 strings still work; they are the same strings.

### 5.3 Custom cache managers

If you implement `IDeliveryCacheManager` yourself, the factory contract is now explicit and a manager that
keeps stale copies for fail-safe must honour it: a factory that returns `null` means the origin has no value
for the key - do not cache, and drop any stale copy you hold - while a factory that throws means the origin
could not be reached, which is when a stale copy may be served. In 19 both cases arrived as `null`, and a
fail-safe manager could go on serving an item the API had answered `404` for. A manager that simply awaits the
factory is unaffected.

`CacheResult<T>` gained `FromFactory` in 20.0.0-rc.1 and `IsStale` in 20.0: set `FromFactory` when your
factory produced the value during this call, `IsStale` when you served a stale copy. The SDK reads both to
classify the result; a `CacheResult<T>` built with neither is reported as a cache hit.

### 5.4 Distributed cache keys

A hybrid client's Redis keys are now `{KeyPrefix}:{EnvironmentId}:v1:{key}`; the `cache:` and `dep:`
segments are gone and a format version is in. Entries written by 19 are not read; they expire on their own.
Every key also carries the environment id, so two applications on different environments can share one
Redis. Nothing to change in your code.

The built-in managers also behave differently in two situations you may have worked around: a distributed
cache that cannot be reached is worked around instead of throwing out of every cached query, and a memory
cache with a `SizeLimit` no longer refuses every entry. Remove any `try`/`catch` you added for the first.

## 6. Disposal moved to the concrete client

`IDeliveryClient` no longer carries `IDisposable` / `IAsyncDisposable`; `DeliveryClient` does. Disposal
exists for one situation - a client built outside a container, which owns its transport - and the interface
offered a `Dispose()` that, on the container path, released nothing and must not be called.

`await using var client = DeliveryClient.Create(...)` is unchanged, and so is every DI usage. The only code
that breaks widened the result to the interface and then disposed it:

```csharp
// 19 - no longer compiles
IDeliveryClient client = DeliveryClientBuilder….Build();
client.Dispose();

// 20 - keep the concrete type, or use var
var client = DeliveryClient.Create(...);
client.Dispose();
```

## 7. Removed from the public API

| Removed | Instead |
|---|---|
| `DeliveryClientFactory` (now internal) | Resolve `IDeliveryClientFactory` from the container; it is unchanged |
| `IItemTypingStrategy` (now internal) | `ITypeProvider`, registered on `delivery.Services` |
| `IContentDeserializer` | Nothing; it could not be implemented - its result had to be an internal type |
| `RefitSettingsProvider` (now internal) and `configureRefit` | Nothing; every setting it exposed was load-bearing |
| `DeliveryCacheServiceCollectionExtensions` and the old builder caching extensions | The `Use…` methods of [§5](#5-caching-attaches-to-the-builder) |
| `QueryEnumerationExtensions` | `EnumerateAsync().AsPages()`, [§2](#2-a-failed-page-throws) |

Two more are visible only in narrow cases. The source generator emits its `ContentTypeCodenameAttribute` as
`internal`, so a project that exposed the attribute across an assembly boundary must stop; one that only
applies it to its own models is unaffected. And `ThrowOnMissingResolver` is now declared on
`IHtmlResolverBuilder` returning the interface, so code that assigned its result to the concrete
`HtmlResolverBuilder` needs `var` or the interface.

## 8. Smaller changes you may notice

- **`PurgeAsync` throws on failed or circuit-breaker-skipped distributed writes and backplane publications.**
  This also changes behavior from 20.0.0-rc.3. The method still returns `Task`, and both `allowFailSafe`
  modes are affected. Local invalidation may already have happened when the call throws. Allow the
  exception to reach a retrying caller, or catch and log it if your application deliberately treats
  purge as best-effort. Ordinary cache reads remain fail-open.
- **`DeliveryOptions.Timeout`** bounds the whole call, retries and backoff included. Unset by default; set it
  and it always wins, whatever the pipeline. It replaces the `HttpClient.Timeout` override that the 19 docs
  showed.
- **An application's own `JsonSerializerOptions` registration is no longer adopted** as the SDK's wire
  serializer. The SDK keeps its serializer under a type only it names; a `JsonSerializerOptions` you
  register stays yours. In 19 it was silently taken over, and without the SDK's converters typed models came
  back empty, so nothing that worked depended on it.
- **Filter parameters are emitted in declaration order**, so request URLs in logs and traces differ.
  Results and cache keys do not.
- **The `Type`-keyed `WithContentResolvers` overloads** are marked `EditorBrowsable(Advanced)`. They still
  work; `WithContentResolver<TModel>` is what the docs lead with.
- **The cache logs under one category**, `Kontent.Ai.Delivery.Caching.FusionCacheManager`, and FusionCache's
  own diagnostics log under `ZiggyCreatures.Caching.Fusion.FusionCache` once logging is registered.
- **Cache invalidation is remembered for ten days** rather than thirty seconds, and a purge on one client
  no longer empties other clients sharing the store. Both were defects; nothing to change.

## What did not change

- Every query builder, filter, projection and pagination method, and the shapes of their results.
- `IDeliveryResult<T>`: `IsSuccess`, `Value`, `Error`, `StatusCode`, `ResponseSource`, `DependencyKeys`.
- Generated models, `ITypeProvider`, and the source generator's output for your own models.
- Rich text: `HtmlResolverBuilder`, every `With…` resolver, `ToHtmlAsync`.
- `IDeliveryClientFactory` and named clients.
- `DeliveryCacheOptions` and its policy: expiration, fail-safe, jitter, eager refresh.
- Every way of supplying options - a delegate, configuration, a pre-built instance - through the builder's
  `Options` ([§4.1](#41-every-registration-form)).
