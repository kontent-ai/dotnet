# Upgrade Guide: Kontent.Ai.ModelGenerator 10 → 11

This guide covers upgrading the `Kontent.Ai.ModelGenerator` CLI tool and the
`Kontent.Ai.ModelGenerator.Core` library, which ship in lockstep on one version, from 10.x to 11.0.0.
Later 11.x releases are described in the
[changelog](https://github.com/kontent-ai/dotnet/blob/main/src/model-generator/CHANGELOG.md).

Most of the work is on the tool's *runtime*, not on what it emits. Delivery output changes in the
header comment of each file and in the edge cases [§5](#5-the-emitted-code) lists; Management models
have to be regenerated. If you generate models from the CLI, §1–§5 apply. §6 is only for code that
references `Core` and subclasses its generators.

## At a glance

| Change | Effort |
|---|---|
| `net8.0` → `net10.0` | Install the tool with the .NET 10 SDK; a project referencing `Core` moves to .NET 10. See [§1](#1-net-10) |
| `--withtypeprovider` / `-t` removed | Delete the flag; the Delivery SDK generates its own provider. See [§2](#2---withtypeprovider-is-gone) |
| Arguments and configuration validated up front | A bad `--environmentId` or `-b` name fails before any request. See [§3](#3-arguments-are-validated-before-the-run) |
| `appSettings.json` key `BaseClass` → `BaseRecord` | Rename the key in your config file. See [§4](#4-appsettingsjson-baseclass--baserecord) |
| Generated output | Delivery: a header diff, plus edge cases. Management: regenerate. See [§5](#5-the-emitted-code) |
| `Core`: removed and changed public API | Only if you subclass the generators. See [§6](#6-core-library-api) |

## 1. .NET 10

Installing or updating the tool needs the **.NET 10 SDK**, and running it needs the .NET 10 runtime. An
older SDK fails with `Settings file 'DotnetToolSettings.xml' was not found in the package` — check a
`global.json` that pins an older SDK, and your CI image.

```bash
dotnet tool update -g Kontent.Ai.ModelGenerator   # a global install
dotnet tool update Kontent.Ai.ModelGenerator      # a local tool manifest
```

`Kontent.Ai.ModelGenerator.Core` targets `net10.0`, so a project still on .NET 8 cannot reference this
release — restore fails with `NU1202`. Move that project to .NET 10 first. `Core` now depends on
`Kontent.Ai.Delivery` 20.0 (10.2.0: 19.2) and `Kontent.Ai.Management` 9.0, so referencing it moves the
project to Delivery 20 — see the
[Delivery 19 → 20 guide](https://github.com/kontent-ai/dotnet/blob/main/src/delivery/docs/upgrade/19-to-20.md).

What the *generated models* need is separate: Delivery models need `Kontent.Ai.Delivery` 19.0 or newer,
and `--nullability semantic` needs 19.2.0 for `RichTextContent.Empty`. Management models need
`Kontent.Ai.Management` 9.0 or newer.

## 2. `--withtypeprovider` is gone

```bash
# Before
KontentModelGenerator -i <environmentId> --withtypeprovider true

# After
KontentModelGenerator -i <environmentId>
```

`--withtypeprovider` / `-t`, `CodeGeneratorOptions.WithTypeProvider` and the `TypeProviderCodeGenerator`
behind them are removed; the tool refuses the flag with `Unsupported parameter`. A `WithTypeProvider` key
in `appSettings.json` is ignored — delete it. `Kontent.Ai.Delivery.SourceGeneration` emits a
`GeneratedTypeProvider` at compile time from the `[ContentTypeCodename]` attributes the generator already
writes, and the SDK discovers it at runtime — so there is nothing left for a hand-written provider to do.
Reference the source-generation package from the project that compiles your models and delete any
generated `CustomTypeProvider.cs` you were carrying.

## 3. Arguments are validated before the run

The tool used to check only that an environment id was present, so `-i not-a-guid` was accepted and the
run failed later against the API with a less obvious message. It now runs the SDK's own options
validation before making any request:

```
$ KontentModelGenerator -i not-a-guid
The delivery configuration is not valid:
  - EnvironmentId: The environment ID must be a valid GUID.
```

`-b` / `--baseRecord` with a value that is not a valid C# record name is refused now — previously it
emitted `public partial record My-Base`, which did not compile.

The 10.3.0 betas, which brought Management mode back, accepted arguments that belong to the other mode.
These are refused now: `-k` / `--apiKey`, or `--ManagementOptions:*`, without `-m` (the betas generated
Delivery models over your output directory); `--DeliveryOptions:*`, `-p` / `--projectid` or
`--nullability` with `-m` (the betas ignored them).

### The startup line changed

Update a script that matches the first line printed; 10.x printed
`Models were generated for delivery-sdk-net version <version>`.

## 4. `appSettings.json`: `BaseClass` → `BaseRecord`

The option was renamed when generated models became records; the shipped template listed the old name
until this release. `BaseClass` is still read as an alias, but rename the key in your own config file:

```diff
 {
-  "BaseClass": "ContentBase"
+  "BaseRecord": "ContentBase"
 }
```

The command-line forms `-b` / `-r` / `--baseRecord` are unchanged, and `--baseClass` is still accepted.

## 5. The emitted code

**Delivery models change in their header comment.** Every file's header now links to
`https://github.com/kontent-ai/dotnet/tree/main/src/model-generator` instead of
`https://github.com/kontent-ai/model-generator-net`. Anything else that differs from `10.2.0` is one of
these:

- With `-b`, the `{BaseRecord}Extender.cs` file the tool rewrites on every run drops its
  `using System;` and `using Kontent.Ai.Delivery.Abstractions;`.
- One of the two collisions at the end of this section.

`--nullability` still defaults to `strict`. The switch to `semantic` that 10.2.0 announced for the next
major did not happen in 11.0.

**Management models have to be regenerated.** 10.0.0 removed the 9.x Management mode, and the 10.3.0
betas brought it back on the modernized `Kontent.Ai.Management`. Since the betas, its identity attributes
are renamed to match `Kontent.Ai.Management` 9.0.0:

| Before | Now |
|---|---|
| `[KontentType]` | `[ContentType]` |
| `[KontentElement]` | `[ContentElement]` |
| `[KontentEnumValue]` | `[ContentOption]` |

Other Management changes since the betas:

- A single-choice multiple-choice element generates `TEnum?` instead of `IEnumerable<TEnum>?`.
- The emitted file carries `using Kontent.Ai.Management.Models.Shared;`; without it, a type with linked
  items, subpages or taxonomy did not compile.
- Delivery-only names are no longer reserved: an element named `content_type_codename` keeps its name
  instead of becoming `_ContentTypeCodename`, and an `x` / `x_codename` pair no longer drops one of them.
- With `-m -b`, the betas' base record carried `using Kontent.Ai.Delivery.Abstractions;`, which does not
  compile in a Management project. The tool keeps an existing base-record file, so delete it before
  regenerating, or remove the `using` by hand.

In both modes, two collisions now skip the offending element or type with a warning:

- Two element codenames that PascalCase to the same identifier (`my_element` and `my__element`), which
  declared the same constant twice and did not compile.
- Two content types that sanitize to the same file name (`my_type` and `my__type`). The last one written
  used to replace the other; now the first is kept.

If a regenerated model is missing something, look for those warnings — the content model has a
collision the old version hid.

## 6. `Core` library API

Only relevant if you reference `Kontent.Ai.ModelGenerator.Core` and extend its generators. The CLI is
unaffected.

| Removed or changed | Replacement |
|---|---|
| `ClassCodeGenerator.Properties` | `protected virtual GetProperties()` — it rebuilds the syntax nodes per call, which a property implied was free |
| `DeliveryClassCodeGeneratorBase` (incl. `PropertyCodenameConstants`, `GetFieldDeclaration`) | Removed; folded into the sealed `DeliveryClassCodeGenerator`, with no replacement |
| `IClassDefinitionFactory`, `IManagementElementService` | Removed; `ClassDefinitionFactory.CreateClassDefinition(...)` and `ManagementElementService.Build(...)` are static with the same signatures |
| `IDeliveryElementService`, `DeliveryElementService`, `DeliveryCodeGeneratorBase` | Removed; `DeliveryCodeGenerator` reads `element.Value.Type` directly and derives from `CodeGeneratorBase`. Its constructor is `(options, outputProvider, deliveryClient, classCodeGeneratorFactory, logger)` |
| `IClassCodeGeneratorFactory.CreateClassCodeGenerator(..., IUserMessageLogger logger, bool customPartial)` | The `logger` and `customPartial` parameters are gone, and the interface gained `CreateManagementClassCodeGenerator(...)`, which an implementation has to add |
| The `CodeGeneratorBase` constructor's `classDefinitionFactory` parameter, the `ClassDefinitionFactory` field | Removed; `ClassDefinitionFactory` is static |
| `ClassDefinition` constructor | Gained `bool emitsCodenameConstants = true`; recompile against the new package |
| `PartialClassCodeGenerator`, the `customPartial` flag, `ClassCodeGenerator.OverwriteExisting` | Removed; the second-partial emission path was unreachable |
| `CodeGeneratorBase.FilenameSuffix`, `GetFileClassName` | Removed; the suffix had been empty since single-file generation |
| `ClassCodeGenerator.IsRecord`, `UseFileScopedNamespace` | Removed; every generator overrode both to `true` |
| `ClassDefinition.AddPropertyCodenameConstant`, `CodeGeneratorBase.AddProperty(Property, ref ClassDefinition)` | `ClassDefinition.AddProperty` now registers the property and its codename constant together |
| `Property.ObjectType`, `IsNullable`, `HasInitializer`, `RequiresDefaultInitializer`, `IsDateTimeElementType`, `IsRichTextElementType`, `IsModularContentElementType` | Removed; unreachable from any emission path |
| `TextHelpers.GetEnumerableType`, `GetUpperSnakeCasedIdentifierName` | Removed |
| `IOutputProvider.Output` returns `void` | Returns `bool` — `true` when it wrote the file, `false` when the file existed and `overwriteExisting` was not set. A custom implementation adds `return true;` |
| `CodeGeneratorOptions` properties | Nullable-annotated |
| `Kontent.Ai.ModelGenerator.Options` namespace | `Kontent.Ai.ModelGenerator.CommandLine` (CLI assembly only; `Core` never had it) |

`DeliveryClassCodeGenerator` and `ManagementClassCodeGenerator` are both `sealed`, so a custom class
emitter derives from the abstract `ClassCodeGenerator`. `CodeGeneratorBase`, `DeliveryCodeGenerator` and
`ManagementCodeGenerator` stay open, with `GetClassCodeGenerators` as a protected virtual hook.
