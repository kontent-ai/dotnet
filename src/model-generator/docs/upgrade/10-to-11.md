# Upgrade Guide: Kontent.Ai.ModelGenerator 10 → 11

This guide covers upgrading the `Kontent.Ai.ModelGenerator` CLI tool and the
`Kontent.Ai.ModelGenerator.Core` library, which ship in lockstep on one version.

Most of the work is on the tool's *runtime*, not on what it emits: **Delivery output is unchanged**
for any content model that produced valid code before. Management output changed and has to be
regenerated. If you only generate Delivery models from the CLI, §1 and §2 are the whole upgrade. Everything from §5 on affects code that references `Core` and subclasses its
generators — a much smaller audience.

## At a glance

| Change | Effort |
|---|---|
| `net8.0` → `net10.0` | Install the .NET 10 runtime; a project referencing `Core` moves to .NET 10. See [§1](#1-net-10) |
| `--withtypeprovider` / `-t` removed | Delete the flag; the Delivery SDK generates its own provider. See [§2](#2---withtypeprovider-is-gone) |
| Arguments validated up front | A bad `--environmentId` now fails immediately, and every problem is reported at once. See [§3](#3-arguments-are-validated-before-the-run) |
| `appSettings.json` key `BaseClass` → `BaseRecord` | Rename the key in your config file. See [§4](#4-appsettingsjson-baseclass--baserecord) |
| Generated output | Delivery: nothing to do. Management: regenerate. See [§5](#5-the-emitted-code) |
| `Core`: removed and changed public API | Only if you subclass the generators. See [§6](#6-core-library-api) |

## 1. .NET 10

The tool needs the **.NET 10 runtime** to run. Reinstall it after upgrading the runtime:

```bash
dotnet tool update -g Kontent.Ai.ModelGenerator
```

`Kontent.Ai.ModelGenerator.Core` targets `net10.0`, so a project still on .NET 8 cannot reference this
release — restore fails with `NU1202`. Move that project to .NET 10 first.

This is separate from what the *generated models* need, which has not changed in this release:
Delivery models need `Kontent.Ai.Delivery` 19.0 or newer, Management models need `Kontent.Ai.Management`
9.0 or newer, and `--nullability semantic` needs Delivery 19.2.0 for `RichTextContent.Empty`.

## 2. `--withtypeprovider` is gone

```bash
# Before
KontentModelGenerator -i <environmentId> --withtypeprovider

# After
KontentModelGenerator -i <environmentId>
```

`--withtypeprovider` / `-t`, `CodeGeneratorOptions.WithTypeProvider` and the `TypeProviderCodeGenerator`
behind them are removed. `Kontent.Ai.Delivery.SourceGeneration` emits a `GeneratedTypeProvider` at
compile time from the `[ContentTypeCodename]` attributes the generator already writes, and the SDK
discovers it at runtime — so there is nothing left for a hand-written provider to do. Reference the
source-generation package from the project that compiles your models and delete any generated
`CustomTypeProvider.cs` you were carrying.

## 3. Arguments are validated before the run

The tool used to check only that an environment id was present, so `-i not-a-guid` was accepted and the
run failed later against the API with a less obvious message. It now runs the SDKs' own options
validation before making any request, and reports **every** problem at once rather than the first:

```
Invalid value for --nullability: 'NONSENSE'. Allowed values: strict, semantic.
Failed to run due to invalid configuration.
```

Three combinations that used to be tolerated now fail:

- `-k` / `--apiKey` without `-m` — previously it generated Delivery models over your output directory.
- `--nullability` with `-m` — Delivery-only, previously accepted and ignored.
- `-b` / `--baseRecord` with a value that is not a valid C# record name — previously it emitted
  `public partial record My-Base` and nothing compiled.

If a script passes any of these, it fails now rather than producing the wrong thing.

## 4. `appSettings.json`: `BaseClass` → `BaseRecord`

The option was renamed when generated models became records; the shipped template listed the old name
until this release. Rename the key in your own config file:

```jsonc
{
-  "BaseClass": "ContentBase"
+  "BaseRecord": "ContentBase"
}
```

The command-line form `-b` / `-r` / `--baseRecord` is unchanged.

## 5. The emitted code

**Delivery models are byte-identical** to `10.2.0`. Regenerating is safe and produces no diff.

**Management models have to be regenerated.** The mode has only ever shipped in prereleases, and its
identity attributes are renamed to match `Kontent.Ai.Management` 9.0.0:

| Before | Now |
|---|---|
| `[KontentType]` | `[ContentType]` |
| `[KontentElement]` | `[ContentElement]` |
| `[KontentEnumValue]` | `[ContentOption]` |

The emitted file also carries `using Kontent.Ai.Management.Models.Shared;`; without it, a type with
linked items, subpages or taxonomy did not compile.

Two cases that previously emitted code which **did not compile** now skip the offending element or type
with a warning instead:

- Two element codenames that PascalCase to the same identifier (`my_element` and `my__element`), which
  declared the same constant twice.
- Two content types that sanitize to the same file name (`my_type` and `my__type`), where the second
  silently overwrote the first.

If a regenerated model is missing something, look for those warnings — the content model has a
collision the old version hid.

## 6. `Core` library API

Only relevant if you reference `Kontent.Ai.ModelGenerator.Core` and extend its generators. The CLI is
unaffected.

| Removed or changed | Replacement |
|---|---|
| `ClassCodeGenerator.Properties` | `protected virtual GetProperties()` — it rebuilds the syntax nodes per call, which a property implied was free |
| `DeliveryClassCodeGenerator.PropertyCodenameConstants` | `GetPropertyCodenameConstants()` |
| `IClassDefinitionFactory`, `IManagementElementService` | Removed; `ClassDefinitionFactory.CreateClassDefinition(...)` and `ManagementElementService.Build(...)` are static with the same signatures |
| `IDeliveryElementService`, `DeliveryElementService`, `DeliveryCodeGeneratorBase` | Removed; `DeliveryCodeGenerator` reads `element.Value.Type` directly |
| `PartialClassCodeGenerator`, the `customPartial` flag, `ClassCodeGenerator.OverwriteExisting` | Removed; the second-partial emission path was unreachable |
| `CodeGeneratorBase.FilenameSuffix`, `GetFileClassName` | Removed; the suffix had been empty since single-file generation |
| `ClassCodeGenerator.IsRecord`, `UseFileScopedNamespace` | Removed; every generator overrode both to `true` |
| `ClassDefinition.AddPropertyCodenameConstant`, `CodeGeneratorBase.AddProperty(Property, ref ClassDefinition)` | `ClassDefinition.AddProperty` now registers the property and its codename constant together |
| `Property.ObjectType`, `IsNullable`, `HasInitializer`, `RequiresDefaultInitializer`, `IsDateTimeElementType`, `IsRichTextElementType`, `IsModularContentElementType` | Removed; unreachable from any emission path |
| `TextHelpers.GetEnumerableType`, `GetUpperSnakeCasedIdentifierName` | Removed |
| `IOutputProvider.Output` returns `void` | Returns `bool` — `true` when it wrote the file, `false` when the file existed and `overwriteExisting` was not set. A custom implementation adds `return true;` |
| `Kontent.Ai.ModelGenerator.Options` namespace | `Kontent.Ai.ModelGenerator.CommandLine` (CLI assembly only; `Core` never had it) |

`DeliveryClassCodeGenerator` and `ManagementClassCodeGenerator` are both `sealed`, so the only
extension point left is the abstract `ClassCodeGenerator`.
